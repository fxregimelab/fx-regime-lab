# FPI execution trust: independently verify the output

27 September 2026. Leaf25.2. Proposal for parent adoption, with an offline experiment. No production authority, executable release, database privilege or consumer has been installed.

Use a protected local verifier to rerun the approved parser, selector and normalizer on retained inputs. Accept the independently produced result, and reject a supplied result unless every output agrees. This establishes that an approved implementation reproduces an output. It does **not** establish that an earlier claimant executed that implementation. Keep that distinction in the record name and public explanation.

The experiment executes the current parser against both pinned private original reports. All 19 complete date outputs agree with the earlier retained row inspection, including every INR component, every published USD component and conversion rate. A different, internally reconciled INR claim is rejected even though its net total is unchanged. Actual copied parser/dependency bytes are altered and rejected against an unchanged synthetic approval fixture. That fixture is test authority only; it confers no production approval.

## Two viable designs

| Choice | What provides authority | Cost and limit |
|---|---|---|
| Separately authenticated runner attestation | A runner identity unavailable to the claimant records the measured release, exact inputs and observed outputs. SQL grants or a verified signature establish who asserted it. | Useful when a remote execution cannot be replayed or execution history itself matters. Requires protecting the runner and its credentials, approval distribution, replay/conflict rules and revocation. A signature proves the signer made the statement, not that correct code ran. |
| Independent deterministic recomputation | A protected verifier selects its locally approved release and retained inputs itself, executes it, compares the entire claimed output and retains its own result through an exclusive database role. | Fits these bounded pure computations. Avoids remote signing infrastructure and trusting the original worker's claim. Still requires a real release authority and protected verifier/database identity. Replay cannot authenticate acquisition timestamps or reconstruct missing decision visibility. |

Choose recomputation. One verifier can own parser verification and saved-read selection/normalization. Do not add an attestation service, custom signing keys, remote hardware attestation or a second general orchestration framework for this step. The resulting database record is still an authenticated statement by the verifier, labelled `INDEPENDENT_RECOMPUTATION`, rather than proof of original worker execution. Prefect can request work; scheduling identity alone is not verification authority.

## Practical authority and release manifest

The owner or an explicitly delegated release operator approves a specific reviewed release digest outside the ordinary parser caller's write access. The parent adopting this design is not that deployment approval. A checked-in manifest, caller-supplied expected hash, local Git branch, lease or this probe's successful marker is insufficient.

Use one protected deployment root containing an append-only approval file and immutable release directories. The verifier OS account has read/execute access, with no release write access. The ordinary pipeline/parser claimant cannot write the root, choose another root, change the verifier launcher or obtain its database identity. The release operator owns updates. The launcher reads the approved digest from this fixed root; a request supplies an identifier to resolve, never a filesystem path, Python expression, import name, executable body or download URL. OS administrator access remains trusted. These account/permission separations must be checked on the actual deployment host before activation; they do not exist merely because this report names them.

The canonical release manifest has version `fpi-execution-release-v1` and these exact categories of content:

1. Reviewed source revision plus every packaged application file's relative path, byte length and SHA-256, including package initializers, observation/capture/parse codecs, selector/qualification adapters, normalizer and the runner wrapper. Git revision alone is insufficient in this dirty checkout.
2. Entry points for `PARSE` and `DECIDE`, exact argument/result codec versions, exception-to-failure-code mapping, and parser/selector/feature semantic versions. The future qualification-v2 selector is a new release; do not attach it to v1 hashes.
3. The full executable environment identity: Python distribution/image digest and platform/architecture; exact dependency wheel filenames and wheel hashes, installed file inventory including native extensions and native-library closure, and explicit optional-package presence/absence. No floating dependency resolution at execution time.
4. Startup recipe, fixed import roots, standard-library source/binary identity, allowed environment names and non-secret values, timezone/locale/encoding/hash-seed/thread settings, parser backend, CPU/native-numeric constraints, and execution/size/resource limits. Supply the policy as a hashed document; do not duplicate its mutable values in environment variables.
5. Digests and locations by content ID of retained executable payloads and input/output codec definitions. Locations resolve only through protected local release storage. Paths reject traversal/links/duplicates. Exact runtime-image retention may be simpler than reconstructing a package closure; either way, its bytes must remain available and match the approved digest.

Canonical ASCII JSON, exact keys/types, sorted compact encoding, no duplicate keys/nonfinite numbers and a versioned domain define `release_sha256`. The final frozen schema and size limits belong in the next parent-owned contract. The above list is the minimum coverage to make that schema honest; this report does not pretend a complete release has already been built.

Existing artifact storage permits at most5MB per body and kinds PARSER/SELECTOR only. It cannot retain a full Python/NumPy runtime. Use a small canonical code/dependency manifest as the artifact body, and separately retain the exact executable payload in protected content-addressed release storage. The artifact's identity hashes that manifest body; its manifest names the runtime payload digest. Do not silently enlarge the SQL field, stuff credentials in a bundle, or claim a manifest hash means its referenced payload is present. For DECIDE, the SELECTOR artifact manifest must also bind the normalizer/codec release; the versioned decision policy must bind that release. A `feature_version` string alone is insufficient. No NORMALIZER artifact enum extension is needed for this arrangement.

No production credential or signing secret was read, generated or proposed as if it already exists. Production still needs provisioning of a verifier database identity distinct from the ordinary archive caller. Reusing a service-role credential accessible to that caller would defeat this design.

## Small interface at the execution seam

The proposed deep module exposes two operations. These are contracts to implement later, not callable functions added by this leaf:

```python
verify_retained_fpi_parse(parse_id: str) -> FpiVerificationReceipt
compute_retained_fpi_decision(read_id: str) -> FpiVerifiedDecisionReceipt
```

The caller supplies only a retained identity. The central-writer adapter loads canonical retained records and approval references; the protected runner resolves its approved local release. The compute subprocess receives bounded canonical input bytes over a private pipe, has no credentials or network access, and cannot load uploaded code. Its output returns through the same strict codec. Central writer publishes the accepted result. The ordinary caller cannot provide the verifier's measured manifest, approval root, successful status or computed output as authoritative arguments.

**PARSE input and comparison.** Load the complete capture and parse record through the restore codec, verify raw/envelope/parser artifact/record hashes, and resolve the artifact to an approved local release. Execute the parser on exactly the retained original body, source URL and retrieval time. Compare ordered date count, each complete canonical INR document, each complete USD/conversion document, hashes, date and derived net; also validate the parser-returned source/version/time metadata. Compare success/failure and a versioned bounded failure code. Never accept a partial date match or net-total-only match. Retained `recorded_at` is compared as envelope metadata, not regenerated from the replay clock or claimed as original execution time. A well-formed result that differs is `OUTPUT_MISMATCH` and cannot qualify.

The parser's `first_seen_at = retrieved_at` is a construction convenience already documented by the parser. Recomputing it does not create durable first-seen authority. Original receipts with seven-digit precision are checked against pinned originals and conservatively normalized only by the established import adapter. Source timing/acquisition trust remains separate. Arbitrary previously stored failure codes with no approved exception mapping stay unverified.

**DECIDE input and output.** Load the exact durable read identified by `read_id`, including its completeness scope, all referenced immutable records, qualification-v2 heads/witnesses, capture-order evidence and parser-verification identities. Verify the read/policy/release identities together. Never replace the saved input with today's heads. Execute the approved selector and retain every status, current/history membership/value identity, exclusion/reason and parse diagnostic, not only the selected numeric series.

For AVAILABLE selection, convert integer hundredths of crore to float crore exactly once; supply current separately from chronological strictly prior history and pass the frozen window explicitly to the approved normalizer. For other selection states retain missing output and its reason; do not turn zero/None into one another. Retain a canonical feature-input document (selected IDs, integer amounts, ordered history, window, feature version/release), its hash and exact normalized result. The result codec should use null for unavailable or the finite IEEE754 binary64 bits as sixteen lowercase hexadecimal digits; validate range[-1,1], and define zero canonicalization. Public numeric conversion follows that codec. This avoids approximate decimal comparison hiding a changed numerical result. Different approved platforms that produce different bits require separate releases/results, not a broad floating tolerance.

The final output identity binds read hash, policy hash, release hash, selection hash, feature-input hash, exact feature result and missingness reasons. A replay of an old saved read uses its original release or reports missing executable dependency. It does not silently upgrade. Consumer wiring and actual live/staged/replay equality remain acceptance work; this leaf runs the real parser only.

## Durable verification and authority checks

Keep release approval, successful verification and business qualification separate. A correct replay can still be economically unsuitable, unqualified, stale or based on unauthenticated acquisition. The frozen qualification-v2 evidence hash remains a reference; the SQL ACCEPT path must resolve it to a valid verification record for that exact parse and an approved release. A caller writing `ACCEPT` or rehashing a document cannot create that authority.

Proposed private append-only records:

| Record | Identity and immutable content |
|---|---|
| Release approval | Operator-assigned approval ID, manifest/release digest, artifact digests, permitted operations, activation scope, and recorded operator identity/time. Authenticated deployment administration, never ordinary service-role self-approval. Revocation is a separate append-only action. |
| Verification request | `request_sha256 = H(canonical(version, mode, retained_input_identity, input_hash, release_sha256, approval_id))`. Retained input means exact parse record/capture or saved read/policy; identity is fixed before execution. |
| Verification result | Request ID, exact input/release/output hashes, method `INDEPENDENT_RECOMPUTATION`, approved codec versions, verifier principal derived from database authentication, and server-stored time. No caller-supplied verifier name as authority. Exact canonical text is retained. |
| Decision output | Complete selection plus feature-input/output documents and their hashes, bound to the verification result and read. Accepted publication is atomic with its verification link. |

All writes are new operations in `pipeline/src/db/writer.py`. A future `append_fpi_verified_result` RPC must be executable only by the dedicated verifier database role. Ordinary capture/parse archivers cannot invoke it or write its tables; approval administration uses a separate deployment role. Anonymous/authenticated clients have no access. Enforce fixed search paths, exact role grants, no direct table writes and append-only protection as in the existing private storage contract. SQL still checks canonical identity/reference constraints and derives the authenticated principal; it does not execute Python or authenticate the result by rehashing it. The trusted verifier is the party asserting the computation.

SQL membership ACCEPT verifies the exact successful parser verification and active approval according to the adopted policy. The one-statement saved-read transaction observes the approval/revocation state and verification references with qualification/candidate evidence. Save those exact trust-state references; a later approval withdrawal prevents new decisions but does not mutate a saved historical read. Historical replay can reproduce revoked releases in a controlled audit mode and must disclose that state; it cannot create a newly eligible live decision.

For selection/normalization, save the computed result and verification link atomically before any consumer receives usable data. Central writer returns only exact receipt keys: request ID, verification ID, retained-input identity/hash, release hash, output hash, server time and inserted boolean. Check exact types, all requested identities, canonical UTC time and detached values. Never trust an echo of caller hashes without the database role and approved release checks. Publication must reference the verified result identity rather than accepting an arbitrary numeric score from its caller.

## Failure, retry and replay rules

- Missing approval/payload, unknown entry point, mismatched code/dependency/runtime/configuration, unsupported codec, incomplete read, absent verification or different output leaves the feature unavailable. Use bounded codes such as `RELEASE_UNAPPROVED`, `EXECUTABLE_MISSING`, `EXECUTION_MISMATCH`, `OUTPUT_MISMATCH` and `EXECUTION_UNVERIFIED`; keep raw source, credentials and supplied JSON out of errors.
- Same request identity and identical result returns the original receipt, including original stored time. Only inserted may differ. A timeout after submission is reconciled by request ID through the verifier's writer path before retry; never invent a new timestamp/read/identity to bypass an uncertain result.
- Compute retries reuse the saved input and approved release. A conflicting result under the same request identity rejects and triggers investigation; no last-write-wins or preferred worker. A deliberate new algorithm/policy has a new release/read identity.
- Resource exhaustion, process crash or timeout is operational failure, not a successful empty parse or zero feature. Record attempt metadata separately if needed; only a complete deterministic result can receive verification. Restarting after failure cannot publish a partial result.
- Revocation, input corruption or missing retained executable prevents new verified output. Previously saved evidence remains inspectable. Time of verification is not time of source release, original computation or decision visibility.

## Threat model and deployment decisions

This protects against arbitrary retained artifact bytes, forged or buggy parser/selector outputs, caller-chosen hashes/paths, unnoticed application/dependency changes, accidental environment drift and callers who can archive evidence but cannot modify approved releases or the verifier identity. Verification must measure the actual executed immutable files/runtime and use a clean process, not hash mutable files and then import a different path. Protected deployment permissions prevent ordinary time-of-check/time-of-use changes; an image digest does not independently prove a running kernel.

For the production launcher, build the complete approved environment before release and start a fresh isolated interpreter for each bounded request. Mount or grant its executable tree read-only; use the fixed approved entry point and import roots, remove user-site/PYTHONPATH/sitecustomize injection, and disallow unapproved bytecode caches. Either retain approved bytecode as part of the image or omit caches and compile the approved sources in that clean process. Confirm loaded module origins/native libraries are inside the approved image inventory; reject unknown modules/dependencies rather than learning a new allowlist during the run. The deployment test must demonstrate rejection of changed source, stale/substituted bytecode, shadowed imports, altered dependencies and configuration, and unauthorized release replacement. Do not allow a long-lived caller to supply preloaded Python objects or monkeypatch the compute worker. Native libraries and dynamic loads require an image/runtime policy and loader checks on the chosen platform. If that closure cannot be enforced, the release remains unapproved for activation.

Compromise of the release operator, verifier OS account, its database identity, database administrator, OS administrator/kernel, runtime supply chain already accepted by the operator, or hardware is outside this model. A compromised verifier can lie. Host administrators can bypass file checks. Separate privileges reduce ordinary caller authority; they are not a claim of protection against privileged compromise. Upstream NSDL authenticity, completeness of market history, acquisition clocks/source finality, economic meaning and predictive usefulness remain separate requirements.

Before deployment, the parent/owner must settle the actual host/account arrangement and prove ACLs, dedicated database-role provisioning and forbidden ordinary-role writes; retain and approve the exact executable environment; freeze the canonical schemas/limits and release revocation semantics; implement bounded clean execution and no-network enforcement; finish complete SQL reads; and verify actual scheduler/staged/replay consumers. No production activation can precede these checks. This is concrete deployment work, not permission to activate based on this report.
