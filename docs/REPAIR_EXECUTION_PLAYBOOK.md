# FX Regime Lab repair execution plan

29 September 2026. This is the execution sequence for the existing [masterplan](../MASTERPLAN.md) and [45-item repair register](REPAIR_REGISTER.md). The register owns issue definitions and acceptance; this document owns dependencies, handoffs and review order. New defects discovered during a packet go into the register before they can be called complete.

## Starting point and finish condition

The local checkout is `codex/frontend` at base HEAD `9fa150538d08ab5a2a6c587976552944f47a724d` with substantial shared, uncommitted repair work. Packets 1–31 have produced 199 passing checks. Six broad gates remain open. Five register items are `VERIFIED LOCAL`, 22 `IN PROGRESS`, 18 `OPEN`, and none `VERIFIED RELEASE`. [The checkpoint](../reports/REPAIR_CHECKPOINT.md) has the latest test receipt and exact limits. A passing check is evidence for its stated behavior; it is not a substitute for a closed issue or a release.

The repair is ready for release review only when each known issue has its stated evidence, old public results have a versioned reconciliation, the whole migration chain and deployed paths have been verified, and live observation windows required by `IDENTITY.md` have actually elapsed. A deterministic failing hypothesis is a valid research result. No process can guarantee the absence of all future bugs or force a 55% forecast result.

The user will run one bounded packet in a new chat, return its output, and ask this chat to verify it before taking the next prompt. The verifier checks the actual diff, source behavior, negative controls and required gates; a worker's own “done” message is never acceptance. Use the same checkout sequentially. Do not start overlapping chats on shared files.

## Packet format and review loop

Every new chat handles one measurable leaf or a small dependency-linked packet. Before edits it records exact owned files and an Unlazy gate, reads the actual symbols and GitNexus impact, and checks whether any database or heavy runtime is needed. It then implements the complete bounded behavior, runs a known-wrong counterexample that fails and a corrected positive case, runs focused checks, and records hashes and limits in a report. The next chat should not inherit a claim that the prior one passed merely from its final answer.

The owner returns the new chat's final response here, together with any file or gate paths it supplies. This chat independently inspects the shared checkout, reruns decisive tests and challenges one claimed property. If evidence fails, the next prompt is a correction for that same packet. If it passes, this chat marks the leaf verified, updates this playbook/checkpoint/register, and gives the next bounded prompt. No new chat should commit, push, deploy, edit production data or change protected identity text without a separate reviewable release decision.

## First packet: D03 rate observation and freshness

The first worker repairs the loss of source timing in the synchronous and asynchronous yield paths, `IngestionSnapshot`, and the rate feature boundary. It must trace current live/staged/replay consumers before choosing an interface. A yield needs its actual source identifier, instrument definition, observed date, available/released time when verifiable, retrieval time, vintage identity when available, units, value and missing reason. Unknown release/vintage cannot be imputed from the spot date or retrieval time. The fixed pair-up economic definitions already accepted in `pipeline/src/signals/rate_inputs.py` must remain intact.

The first gate is a counterexample: a fresh FX spot with a stale yield must never produce a qualified current rate input. Other gates cover valid timely input, monthly/unknown availability, source fallbacks, null/zero distinction, live/staged/replay consistency, bounded logging and old scalar compatibility only where plainly marked unqualified. Source acquisition tests use deterministic fixtures; no provider credentials or live requests are needed. If durable storage requires a schema migration, implement it through the central writer and verify a scratch database before claiming D03 complete. If a provider cannot supply release/vintage truth, keep the feature unavailable and record that exact external gap. The output must identify whether D03 is fully verified locally or remains in progress, with no overstated acceptance.
